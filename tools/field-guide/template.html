Salt SDK Field Guide

Salt is an MPC wallet layer built by traders who wanted more control, less vendor risk and lower costs.

Accounts are MPC wallets, where every key share is generated and held on your own hardware – distributed across co-signers' devices and self-provisioned automated co-signers that Salt calls Robo Guardians. Salt never holds key material, and a smart contract on Arbitrum keeps an encrypted backup of each share for portability and account recovery. It's a novel system of self-sovereignty, built to minimise trust within an MPC setup. Every transaction is checked against the account's policies before the Robo Guardians add their signature.

Normal setup takes around 20 minutes. Once familiar, you can speed run it in under 10 mins. AI can assist with the install (we demo Claude setting up the Robo Guardians below).

Fun factSalt is the only MPC solution that AI agents can discover and use themselves without human assistance – no API keys needed; authentication uses cryptographic keypairs.

Salt is an open system to humans and machines.

This guide takes your team from an empty terminal to a policy-protected account on testnet, using salt-fi as a working reference for each SDK call. Mainnet is also supported.

How a Salt transaction gets signed

An organisation holds your accounts and the collaborators who sign for them. Each organisation has one set of Robo Guardians, the automated co-signers. Policies attach to accounts, one set per chain.

The check runs on the exact transaction the signers will sign. During the ceremony each Robo Guardian hashes the payload it's asked to sign and compares it with the transaction record the policy check ran on. If they differ, it refuses to sign.

Start with salt-fi

salt-fi is a terminal app that walks through Salt end to end: organisations, Robo Guardians, accounts, transfers, swaps and policies. Each menu item is a short, readable use of the SDK, so the source doubles as example code. It's open source under Apache-2.0 and maintained independently by one of Salt's founders; it isn't an official Salt product.

github.com/salt-space/salt-fi · the README documents every menu item.

Set up

You need Node.js 24 or newer, Git, and a throwaway EVM private key for testnet. Never use a key that holds real funds.

git clone https://github.com/salt-space/salt-fi.git
cd salt-fi
npm install
cp .env.example .env     # then set PRIVATE_KEY=0x…
npm run dev:testnet

Pick Getting started the first time. It walks through the five setup steps in order, explains each one, and resumes where you left off:

  1. Create an organisation. You're its owner.
  2. Invite a collaborator. Accounts need at least two collaborators, the owner plus one more.
  3. Set up Robo Guardians.
  4. Create an account. This runs an MPC key-generation ceremony between the signers and the Robo Guardians.
  5. Add a first policy.

Or build your own front end

Salt supports a tenant model, so you can build your own front end on the SDK instead. That gives you more control, and an experience built around how your team works. Ask Salt to approve your tenant domain; localhost works for development. Pass that domain as domain when you create the Salt client. It goes into every sign-in message your users sign, and Salt resolves your tenant from it. You still set up Robo Guardians through salt-fi or Salt's web app.

const salt = new Salt({
  environment: "TESTNET",
  domain: "app.example.com",                   // your approved tenant domain
  siweStatement: "Sign in to Example Treasury", // shown in the wallet prompt
});

Salt's own web app, due for release in November 2026, is built entirely on the Salt SDK.

Signing in: your wallet is your identity

There are no Salt usernames or passwords. You sign in with Sign-In with Ethereum (SIWE): the SDK has your wallet sign a standard login message, and Salt verifies the signature and issues a session token. The key stays on your machine. Nothing goes on-chain and there's no gas to pay.

That wallet's address is who you are in Salt:

  • Organisations invite you by address, and you accept with the same wallet. Your access level (owner, member or agent) is attached to that address, and only owners can change policies.
  • Accounts you co-sign use this wallet in their key-generation and signing ceremonies.
  • Backups are encrypted to this wallet's public key, which Salt recovers from your sign-in signature. Your key-share backups are written to Salt's shard registry contract on Arbitrum, and Salt pays the gas. If you set up the organisation's Robo Guardians, their seed backup is encrypted to your key too. Back the key up like any other.

Give every person and every automated signer on your team its own key. Sessions are issued per environment: testnet.salt.space for testnet and app.salt.space for mainnet. salt-fi asks which to use at launch.

Robo Guardians, installed by Claude Code over SSH

Robo Guardians are your organisation's automated co-signers. They hold key shares for every account, enforce policies by refusing to sign anything the check rejected, and run on a server you control. Each host runs three signers in one Docker container. Their seed is generated on that server and encrypted to the owner's wallet key before an encrypted backup goes to Salt.

salt-fi generates a one-shot install script for any Ubuntu or Debian server, or an AWS CloudFormation link that does the same with no server access. Below, Claude Code installs the script over SSH. These are replays of a real session on testnet, for a demo organisation called Nara Capital.

1 of 3Create the organisation and its setup script

In salt-fi, choose Organisation → Create organisation, accept the offer to set up Robo Guardians, and pick the self-hosted install script. salt-fi writes robo-setup-<org>-<id>.sh to the project folder. It contains the host's one-time setup code, so treat it like a password. It's gitignored.

2 of 3Let Claude Code install it over SSH

Open Claude Code in the salt-fi folder, give it the server, and say what's already running there. For example:

Prompt to Claude CodeSet up Nara Capital's Robo Guardians on my server: ssh -i ~/.ssh/<key> root@<server-ip>. It already runs robos for other organisations. Look first without changing anything, adapt the setup script so it can't collide with them, and show me the changes before you run it.

Claude looked at the server first and found three robos already running there. The stock script expects to be the only robo on a server: it refuses to run next to an existing one, and its Docker install step could upgrade Docker, restarting the daemon and briefly stopping every robo on the box. So Claude gave the new robo its own container name, directory, update job and cron entry, skipped the Docker reinstall, showed the diff, and ran it once approved.

3 of 3Check they're online, then activate them

Back in salt-fi, Robo Guardians → Check robo guardians should list three signers online. They can't sign until the owner activates them. Activate Robo Guardians (2FA) signs a message with the owner's wallet that includes the setup code, and activation consumes that code.

Hosting several organisations' robos on one server

The install script uses a fixed container name (robos) and directory (/salt/robos). For each additional organisation, give its robo its own name and directory, point its update_docker.sh and cron entry at them, and don't reinstall Docker on a server that's already running robos. That's the whole of Claude's change in step 2. The Hostinger guide in salt-fi covers doing it by hand.

The policy layer

Policies are granular rules attached to an account, per chain. Salt evaluates every applicable policy together against each transaction the account proposes, before any co-signing. If a policy is breached, the Robo Guardians won't sign and the SDK throws a PolicyBreachError listing the policies that blocked it.

The six policy types

TypeWhat it constrainsParams
allowed_recipientsOnly these addresses may receive funds.{ recipients: [{ address, nickname? }] }
denied_recipientsThese addresses may not receive funds.{ recipients: [...] }
denied_proposersThese signers may not propose transactions. The addresses sit under recipients for legacy reasons.{ recipients: [...] }
transaction_limit_token_denominatedThe most one transaction may move, per token. The zero address means the native asset.{ limits: [{ address, amount }] }
contract_param_restrictionArguments of specific contract calls.{ restrictions: [{ contractAddress, functionSignature, paramIndex, operator, value }] }
nominated_approversRequired approvals. Not enforced yet, and it can't be created.{ approvers: [{ address }] }

How they combine

  • There's one policy per type per chain. The chain is a chain ID string, or "*" for every chain, and a "*" policy and a chain-specific one of the same type both apply.
  • An allowlist and a blocklist both apply, so an address on both is blocked.
  • Updating a policy replaces its params, so send the full list.
  • Limits are per transaction, not cumulative. An amount of "0" freezes that asset.
  • A contract restriction applies only to calls of its function on its contract, and every restriction a call matches must pass. Two eq restrictions on the same argument can never both hold, so together they block that function entirely.
  • Restriction values aren't validated when saved, and a malformed one blocks every call it matches. Only top-level arguments can be restricted (numbers, addresses, bools, bytes and strings), not struct fields or array elements.

What policies see, and what they don't

  • Limits see native value and direct transfer() calls. A router, bridge or pool that pulls tokens with transferFrom after an approve() isn't limited. To bound that, restrict the token's approve(address,uint256) amount: paramIndex 1, operator lte.
  • For contract calls, an allowlist is checked against the contract being called. To swap, both the token (for the approval) and the router have to be on it. Pin who can be approved with a restriction on the spender: paramIndex 0, operator eq.
  • Signed messages aren't transactions. A Permit2 permit or an off-chain order is typed data, so account policies don't evaluate it. The pull it authorises happens later, in someone else's transaction.
  • Relayed flows leave the policy boundary. Once funds sit in a system whose relayer moves them, such as a privacy pool, those movements aren't the account's transactions.

Check before you submit

runPoliciesCheck evaluates a proposed transaction without signing anything. Fill it the way submitTx will, or the answer won't match what the Robo Guardians see.

const fees = await salt.getGasPrice(421614);
const check = await salt.runPoliciesCheck(accountId, {
  nonce: await salt.getAccountNonce(accountId, 421614),
  from: accountAddress,         // the Salt account's address, not your signer's
  to: router,
  amount: value.toString(),     // native value in wei: native limits read it
  data: calldata,
  network: "421614",
  gas: "500000",
  maxFeePerGas: fees.maxFeePerGas.toString(),
  maxPriorityFeePerGas: fees.maxPriorityFeePerGas.toString(),
});

if (check.policyBreach) {
  for (const policy of check.rejectedPolicies) console.log("blocked by", policy.type, policy.chain);
}

check.networkPolicies lists every policy that was evaluated. A policy on this chain that's missing from it didn't apply to this transaction, which usually means it doesn't constrain what you're doing.

Create policies from code

await salt.createAccountPolicy({
  accountId,
  organisationId,
  type: "contract_param_restriction",
  chain: "421614",
  params: {
    restrictions: [
      // USDC approvals may only go to the router, and never above 250 USDC (6 decimals)
      { contractAddress: USDC, functionSignature: "approve(address,uint256)", paramIndex: 0, operator: "eq", value: ROUTER },
      { contractAddress: USDC, functionSignature: "approve(address,uint256)", paramIndex: 1, operator: "lte", value: "250000000" },
    ],
  },
});

In salt-fi

  • Manage policies is a guided builder for every type you can create, with presets for common contract restrictions.
  • Policy chat takes plain English, such as "cap USDC approvals at 250 on Arbitrum", proposes the exact policy, and asks before applying it. It needs an API key for the language model that powers it, set in .env.
  • Swap, Bridge and the Hinkal deposit check their transactions before submitting and show which policies pass or fail.

Not expressible today

  • Cumulative or time-window limits, such as a daily cap.
  • Time-based access.
  • Enforced human approvals: nominated_approvers isn't enforced yet.
  • "Either A or B" for one contract argument.
  • Separate allowlists for payees and for contracts. One allowlist covers both.

Using the SDK directly

salt-sdk is an ES module that uses top-level await, so your package.json needs "type": "module". It declares Node.js 24 or newer.

npm install salt-sdk viem
import { Salt, PolicyBreachError } from "salt-sdk";
import { createPublicClient, createWalletClient, http, parseEther } from "viem";
import { privateKeyToAccount } from "viem/accounts";
import { arbitrumSepolia, sepolia } from "viem/chains";

// Your signer. On testnet, Salt's key-share registry lives on Arbitrum Sepolia;
// the signer only signs there, and Salt pays the registry gas.
const walletClient = createWalletClient({
  account: privateKeyToAccount(process.env.PRIVATE_KEY as `0x${string}`),
  chain: arbitrumSepolia,
  transport: http(),
});

const salt = new Salt({ environment: "TESTNET", domain: "testnet.salt.space" });
await salt.authenticate(walletClient); // SIWE

const [org] = await salt.getOrganisations();
const [account] = await salt.getAccounts(org.id);

// Send 0.001 ETH on Sepolia. Policies are checked first, and the
// Robo Guardians co-sign only if every one passes.
try {
  const ceremony = await salt.submitTx({
    accountId: account.id,
    to: "0x…",
    value: parseEther("0.001"),
    data: "0x",
    chainId: 11155111,
    userAddress: walletClient.account.address,
    walletClient,
    publicClient: createPublicClient({ chain: sepolia, transport: http() }),
  });
  const { transaction } = await ceremony.wait();
  console.log("broadcast", transaction.broadcastReceipt?.transactionHash);
} catch (err) {
  if (err instanceof PolicyBreachError) console.error("blocked by", err.rejectedPolicies.map((p) => p.type));
  else throw err;
}

The account needs gas on the chain it sends from. On testnet, salt-fi's Assets → Faucet for Salt accounts points you at faucets that work for new accounts.
